# Texas Lake Levels

Statewide water-level monitoring for Texas reservoirs. Similar in spirit to
[LCRA Hydromet](https://hydromet.lcra.org/), but covering all 122 major
reservoirs in the state rather than the six Highland Lakes, and joining
authoritative daily storage figures to real-time gage readings.

**Live: https://lbjtaskforce.com**

This file is the long-form reference: it explains why each subsystem works the
way it does. Alongside it —

| | |
| --- | --- |
| [`AGENTS.md`](AGENTS.md) | Conventions and traps, for anyone (human or agent) editing the code |
| [`docs/data-sources.md`](docs/data-sources.md) | Every upstream feed, its cache window and its quirks |
| [`docs/roadmap.md`](docs/roadmap.md) | What is worth building next, and why |

## Data sources

| Source | What it provides | Cadence | Coverage |
| --- | --- | --- | --- |
| [TWDB Water Data for Texas](https://www.waterdatafortexas.org/reservoirs/statewide) | Elevation, surface area, conservation storage, percent full, full period-of-record history | Daily | 122 major reservoirs |
| [USGS NWIS](https://waterservices.usgs.gov/) (params 62614 / 62615 / 00062) | Lake elevation | ~15 min | ~165 active TX gages |

TWDB is authoritative for *storage*, because turning an elevation into a volume
requires a reservoir-specific area-capacity curve that TWDB maintains. USGS
provides the intraday movement that a once-daily feed cannot.

## How it fits together

```
TWDB recent-conditions.json ──┐
                              ├── matchGage() ──> LakeSummary ──> pages + /api
USGS NWIS instantaneous ──────┘

TWDB per-lake CSV (30day / 1year / all) ──> history charts
```

### Reservoir ↔ gage matching

TWDB and USGS share no identifier and name lakes differently (`Lake Lyndon B
Johnson` vs `LCRA Lk LBJ nr Marble Falls, TX`), so `src/lib/lakes.ts` matches on
position: a gage within **8 km** of the TWDB gage location is accepted outright;
one between **8 and 30 km** is accepted only if the names share a distinctive
token. This resolves **110 of 122** reservoirs.

The 12 unmatched lakes (Amistad, Falcon, Texoma, Toledo Bend, Caddo, Lake
Houston, and others) have no real-time USGS lake-elevation gage — they are
operated by IBWC and USACE, which publish through separate systems. Those pages
fall back to daily TWDB data and say so.

### Slug mapping

TWDB's JSON keys (`BASteinhagen`) differ from its CSV slugs (`b-a-steinhagen`)
in a way that is not mechanically derivable — compare `BoisDArc` → `bois-darc`
against `OCFisher` → `o-c-fisher`. `src/lib/slugs.ts` is generated by pairing the
two on their alphanumeric-only forms:

```bash
npm run sync:slugs   # re-run if TWDB adds or renames a reservoir
```

The script refuses to write a partial map, so a TWDB markup change fails loudly
rather than silently dropping lakes.

### County basemap

`/map` draws all **254 Texas counties** from Census cartographic boundaries,
stored compactly in `src/data/tx-counties.json` (76 KB — rings flattened to
`[lon, lat, …]` and rounded to three decimals, ~90 m):

```bash
npm run sync:counties
```

Geometry is kept in lon/lat rather than pre-baked SVG paths so counties and
reservoir markers project through the **same** function — baking paths risks the
basemap drifting out of register with the dots. The script asserts exactly 254
counties before writing.

The **state outline** is produced by stroking every county ring thickly, then
redrawing each county filled on top, so only the outer perimeter survives.
Deriving it by cancelling shared edges is not possible with this source:
adjacent counties don't share identical vertices (1,741 edges fail to pair), so
that approach yields interior gaps.

A handful of TWDB reservoirs sit outside Texas (Elephant Butte, NM) and would
render clipped and invisible; the map excludes them explicitly and names them in
the caption.

## Rate limiting

TWDB throttles bursts — firing ~100 requests at once returns 502/503. Two
consequences are baked into the design:

- Every upstream fetch is cached via `next: { revalidate }` — 6 h for statewide
  conditions, 12 h for per-lake history, 10 min for USGS.
- Lake pages deliberately **do not** use `generateStaticParams`. Pre-rendering
  all 122 would fire 122 history requests during every build — exactly the burst
  pattern that gets throttled. Pages render on demand and then cache.

## Historical percentile context

TWDB's period of record runs to **86 years** of daily observations (Travis starts
1940-09-30, ~30,600 rows). `src/lib/history.ts` turns that into the answer to
"is this unusual?":

> At 100%, Lake Travis is near its highest on record for this date — above 90% of
> all years since 1940. It was last this high in 2007.

- Percentiles pool the **±3 days** around the target date across every year. A
  single calendar day yields only ~86 samples at best, so the tails are noisy;
  a 7-day window multiplies the sample without smoothing away seasonal signal,
  because reservoirs move slowly.
- The **current year is excluded** from the comparison set, so "last time it was
  this low" can't answer "yesterday" — the question is about other years.
- Bands are computed on **percent full only**. It's the one metric comparable
  across decades: elevation datums and storage capacities get re-surveyed, but
  share-of-conservation-pool stays meaningful. (Capacity re-surveys still make
  cross-decade comparison close rather than exact — the UI says so.)
- The percent-full chart draws the 25th–75th percentile band and median behind
  the actual series.

### Precomputed history

TWDB serves a reservoir's full history only as one large CSV — up to ~1.9 MB
across ~30,600 eight-column rows. Parsing that per request cost 10–30 s on a
cold Cloudflare isolate.

`npm run sync:history` strips it to the two columns percentiles actually need
and stores them positionally in `public/history/<slug>.json`:

```json
{ "first": "1940-09-30", "values": [216, 217, null, 219, ...] }
```

Index is days since `first`; values are percent-full in tenths; `null` marks a
gap. That is roughly **12–15x smaller** (0.44 MB → 38 KB, 1.09 MB → 89 KB) and
needs no CSV parsing at runtime. The files are served as static assets from the
edge, so they never touch TWDB on the request path.

Two details that matter:

- **The precompute is frozen at whenever the script last ran**, so the small
  30-day CSV (a few KB) is layered on top at request time. Without it the
  "current" reading used for percentile comparisons would be as stale as the
  last precompute.
- **The CSV path is still there as a fallback.** A reservoir with no
  precomputed file — Addicks, a dry flood-control basin with almost no
  percent-full readings — falls back to fetching the full CSV.

Derived statistics are additionally cached through `unstable_cache` (see
Deploying), so the work above happens once per revalidate window rather than per
request.

## River flows (inflow / release)

`/lake/[slug]` shows discharge at the nearest gaged reaches above and below the
dam, from the 618 active Texas discharge gages.

Attribution is the hard part, and neither obvious approach works: proximity
fails because a gage 5 km away may be on a different river, and name matching
fails because only a handful of the 618 gages mention a lake at all. So
`npm run sync:flow` uses the **USGS Network Linked Data Index**, which navigates
the real NHD hydrography network — walking `UM` (upstream main) and `DM`
(downstream main) from each dam gage and keeping the nearest site that actually
reports discharge.

That maps **96 of the 110** reservoirs with a dam gage (54 inflow, 85 release).
Validation: Canyon Lake resolves to `08166250 Guadalupe Rv at Spring Branch` and
`08167800 Guadalupe Rv below Canyon Lk` — the correct pair.

Two deliberate honesty constraints:

- **Straight-line distance from the dam is recorded and displayed.** A release
  gage 2 km below the dam is that dam's outflow; one 60 km downstream has picked
  up tributaries and possibly other reservoirs. Users need that to calibrate.
- **The net figure is labelled "gaged net", not a water balance.** Ungaged
  tributaries, rain on the lake surface, evaporation, and direct withdrawals are
  all unmeasured, so it will not reconcile exactly with storage change.
- Reservoirs where one site resolved both upstream *and* downstream (the
  navigation looped, or the dam gage sits off the main stem) are dropped rather
  than published with a meaningless direction.

## Drought Monitor overlay

US Drought Monitor data (NDMC/USDA/NOAA), published weekly on Thursdays, appears
in three places: a county overlay toggle on `/map`, a dedicated `/drought` page,
and a local-conditions panel on each lake page.

Three things the API makes easy to get wrong:

- **Percentages are cumulative.** `d1` already includes D2–D4. Stacking them
  directly double-counts and exceeds 100%, so `exclusiveShares()` converts to
  per-category shares before charting.
- **DSCI is the sum of the five cumulative figures** (0–500). The county
  endpoint doesn't return it, so we compute it — verified against the API's own
  `GetDSCI`: 76.83 → 77.
- **The county endpoint rejects a state-wide `aoi`**, but accepts a
  comma-separated FIPS list. All 254 Texas counties come back in a single
  request (~1.7 KB of URL, ~60 KB of response) rather than 254 round trips.

### Lake → county lookup

Reservoirs are matched to counties by even-odd ray casting over the existing
basemap geometry, testing all rings of a county together so holes and enclaves
resolve correctly.

Containment alone found only 117 of 122 reservoirs. Every miss was a **boundary
dam** — Amistad, Texoma, Toledo Bend, Caddo — gaged essentially on the state or
national line, where the basemap's 3-decimal rounding (~90 m) puts the point
marginally outside Texas. A 25 km nearest-county snap recovers all of them
(Amistad → Val Verde, Toledo Bend → Newton) while correctly leaving Elephant
Butte unassigned, since it sits 139 km inside New Mexico. Final coverage: 121
of 122.

### Framing

The overlay shades each county by the **worst category present anywhere within
it**, which the UI states — a county shaded D3 is not D3 throughout. The lake
and drought pages both note that local drought is context rather than
explanation: reservoirs are filled by watersheds reaching far beyond one county,
and releases are managed.

## River gages layer

`/map` has a **River gages** toggle plotting ~900 active USGS sites statewide,
merged from gage height (00065, ~790 sites) and discharge (00060, ~620) — many
stations report both, so they come back as one marker each from a single
request.

For comparison, LCRA's Hydromet — which this layer is modelled on — covers the
lower Colorado basin only. Its map looks denser than ours did because it plots
rainfall and river gages alongside lakes; on reservoirs themselves we already
covered 121 statewide against its six.

Design notes:

- **Diamonds, not circles.** At this density shape separates the layers faster
  than colour, and colour is already carrying reservoir fill status.
- **Drawn beneath reservoirs.** There are ~7x more river sites; drawn on top
  they bury the lakes.
- Sky blue = reports discharge; grey = stage only.
- Readings are shown on hover, not as permanent labels. Labelling every marker
  was tried and removed: at ~900 river sites plus 121 reservoirs the numbers
  collide into noise, and the hover card carries more useful detail anyway
  (site name, both parameters, reading age).

`compactForMap()` rounds coordinates to four decimals (~11 m) and trims reading
precision before the data is serialised into the page — at ~900 sites the full
response would otherwise be a large chunk of the payload for accuracy no one can
see at statewide zoom.

### NWS flood status

A raw stage reading carries no meaning by itself — 20 ft is routine on one river
and a disaster on another. The NWS National Water Prediction Service
(`api.water.noaa.gov/nwps/v1`, `src/lib/nwps.ts`) defines the
action/minor/moderate/major thresholds per gauge, so gages currently in a flood
category are recoloured on the NWS-standard yellow/orange/red/purple ramp,
drawn slightly larger, sorted to the top of the layer, and labelled in the
hover card and legend.

NWPS and USGS share no identifier in the list endpoint, so the ~1,000 NWPS
gauges are joined to USGS sites **by position** (they are the same physical
installations): nearest within 1 km, grid-bucketed so the join stays linear.
The category legend entries appear only for categories actually present, and
the caption says explicitly when nothing is flooding — silence should read as
"quiet", not "feature broken".

### Flow percentiles

Beyond flood status, every discharge diamond is coloured by where the current
reading sits against that gage's own period-of-record normals for the month —
the WaterWatch-style "high or low for the season?" signal. USGS decommissioned
the WaterWatch service that answered this directly, and the replacement
(`nwis/stat` daily statistics) is ~15 MB statewide — far too heavy for the
request path — so `npm run sync:percentiles` precomputes monthly p10/p25/p50/
p75/p90 thresholds per site into `src/data/flow-percentiles.json` (~120 KB,
~508 of 618 active sites; the rest fail a 10-years-of-record screen).
`classifyFlow()` in `src/lib/flowstats.ts` buckets a live reading at render
time; the thresholds table is server-only, and client components import the
palette from `src/lib/flowclass.ts` so the JSON stays out of the browser
bundle.

The palette is deliberately not WaterWatch's: its red/orange dry end collides
with the NWS flood ramp sharing this layer. Dry runs brown/amber, normal keeps
the layer's sky blue, wet runs blue into indigo. Flood category always wins
the marker colour — "in flood" beats "above normal" as the thing to surface.

### River forecasts

NWS issues actual stage/flow forecast series (~5 days, 3-hour steps) for most
of its gauges — 768 of the 1,039 in the Texas bounding box when last counted.
On lake pages, `ForecastPanel` matches the lake's own gauge and the precomputed
inflow/outflow gages to NWPS points by the same 1 km position join, and charts
any forecasts found (`/gauges/{lid}/stageflow/forecast`, `getGaugeForecast()`
in `src/lib/nwps.ts`) with the forecast peak called out. Dashed line on
purpose: every other series on the page is an observation, and line style is
what keeps a prediction from reading as one.

Whether the panel appears is therefore decided by proximity rather than
availability — plenty of lakes have no forecast gauge within the join, and the
panel simply renders nothing. It streams inside Suspense so that neither the
gauge list nor the per-gauge forecast requests can hold the page. Flow arrives
in kcfs and is converted; `-999` sentinels become nulls; and a gauge with no
active forecast answers 200 with an empty array rather than 404.

## Rainfall

Source is **CoCoRaHS** — the Community Collaborative Rain, Hail & Snow Network,
~2,000 Texas volunteers who read a gauge each morning. One request returns every
Texas report for a date range (~2 MB for 7 days), and rows aggregate to one
total per station.

### Why not USGS precipitation

USGS parameter 00045 looks like the obvious choice — 397 active Texas sites on
the API this project already uses. It was rejected after testing:

- **It mixes incremental and cumulative series.** Summing a single day produced
  a **56-inch** total for one site. Texas's daily record is ~42 inches, so that
  is not a wet day, it is a series where the value is a running total since
  reset. The API does not cleanly distinguish the two conventions, so any
  accumulation built on it is silently wrong for an unknown subset of stations.
- **Payload.** A 7-day window is ~26 MB across 330,000 datapoints; CoCoRaHS is
  ~2 MB and pre-totalled.

The trade-off accepted in exchange: CoCoRaHS readings are manual and taken once
each morning, so unlike the lake and river gauges they are not real-time. The UI
says so.

### Where it appears

- **`/map`** — a Rainfall layer, circles sized by 7-day total and coloured on a
  purple scale kept deliberately distinct from both the reservoir status colours
  and the drought ramp, so three layers can be on at once. Drawn at the bottom
  of the marker stack, since its circles are the largest.
- **`/lake/[slug]`** — 7-day and 24-hour totals near the dam.

**Stations with no measurable rain are not plotted.** About 2,000 stations
report and on a dry day nearly all read zero; plotting them is noise on a
rainfall layer. Absence of a marker means no measurable rain, not no station.

**Lake rainfall is measured near the dam, not across the watershed** — a
catchment can extend hundreds of kilometres upstream, so local rain and inflow
are related but not the same. The panel states this rather than implying
causation.

### Two caching traps hit here

- **`cache: "no-store"` inside `unstable_cache` disables the cache.** Next
  treats a no-store fetch as making its whole scope dynamic, so the surrounding
  cached function silently stopped caching and every cold isolate re-downloaded
  2 MB. Lake pages regressed from ~0.9 s to 5–57 s before this was found.
- **Enrichment must not block the page.** The rainfall panel now renders inside
  a `Suspense` boundary and streams separately. Time-to-first-byte on a cold
  lake page is **58–1053 ms** even when rainfall behind it takes seconds; the
  panel shows a skeleton until it resolves.

### Palette

The USDM ramp is drawn at `DROUGHT_MAP_OPACITY` (0.45), not full strength.
Browser testing showed the collision plainly: at full opacity an orange "Low"
reservoir marker on an orange D2 county is nearly invisible, and a rose
"Critically low" marker on red D3 reads as part of the drought scale. Drought is
context; the reservoirs are the subject.

Legend swatches composite the same colour over `--map-land` at the same opacity,
sharing one constant. Without that they drift: at 0.45 over a dark basemap the
D0 yellow reads olive, so a legend drawn at 100% no longer matches the map it
explains.

### Payload

`alignStorageToWeeks()` joins storage to drought weeks **on the server**. Drought
is weekly and storage is daily back to 1933, so passing the raw series to the
client shipped ~34,000 points — a 2.9 MB page — of which the chart could only
plot the ~1,300 aligned to a drought week, and never anything before 2000. The
page rendered but its charts stayed blank for many seconds while that hydrated.
Aligning server-side cut it to 438 KB (73 KB gzipped) and the charts now paint
within a few seconds.

## Statewide totals

`getStatewideHistory()` reads TWDB's own aggregate (`statewide.csv`), daily
since **1933-07-01** (~34,000 rows). Deriving it from the 122 individual
reservoirs would mean 122 requests and would silently change meaning as
reservoirs enter the monitored set over the decades.

**Non-Texas reservoirs are excluded from every aggregate.** Elephant Butte sits
in New Mexico with 1.96 M acre-feet of capacity and is currently ~2% full;
counting it pulled our statewide figure to 73.8% against TWDB's published 78.3%
— the capacity gap was exactly Elephant Butte's 1,960,900 acre-feet. TWDB tags
it `new_mexico` rather than `texas`, and filtering on that tag reproduces their
number exactly. The reservoir is still listed and browsable; it just doesn't
count as Texas supply.

## Supply outlook

`computeSupplyOutlook()` extrapolates the trailing 60 days of conservation
storage to a depletion date. The window is long enough that one rain event or
release doesn't dominate, short enough to reflect current conditions.

It is labelled in the UI as an extrapolation, not a forecast: it assumes the
recent rate continues unchanged, ignoring seasonality, rainfall and managed
releases, and drawdown normally slows as a reservoir falls. Rates under
1 acre-foot/day are treated as flat rather than projected.

## City water supplies

`/cities` rolls reservoirs up into TWDB's own municipal water-supply systems,
which ship as `municipal_*` tags on the recent-conditions feed — no extra
upstream. `getSupplySystems()` (`src/lib/systems.ts`) groups by tag and
computes a storage-weighted fill per metro area.

Two accounting choices differ from the statewide rollup, deliberately. A
reservoir can serve several systems (Lake Texoma is both Dallas and Texarkana
supply), so systems overlap and are never summed with each other. And
out-of-state members count: Elephant Butte is excluded from statewide totals
but *is* El Paso's principal reservoir supply — which is why El Paso's figure
can sit far below anything on the dashboard. The page caption also scopes the
claim: these are monitored reservoirs only, not groundwater, run-of-river
rights or purchased water.

## USACE gap lakes

Ten reservoirs have no real-time USGS elevation gage. `npm run sync:usace` maps
them onto USACE CWMS time series by proximity to CWMS locations in the Texas
districts (SWT/SWF/SWG).

**Only 2 of the 10 are actually covered** — Texoma (`DENI.Elev.Inst.30Minutes`)
and O. H. Ivie. The rest match a CWMS *location* record that publishes no time
series at all (Amistad, Falcon, Toledo Bend, Caddo, Lake Houston), or are
operated by IBWC and the Bureau of Reclamation, which publish elsewhere. Texoma
is Texas's second-largest reservoir, so the two are still worth having.

Every candidate series is validated against TWDB's own elevation before being
accepted, and anything more than 5 ft off is discarded. That check does real
work: a dam publishes headwater *and* tailwater series with near-identical
identifiers, and picking the tailwater one would report a level tens of feet
wrong. Both accepted mappings agreed with TWDB to 0.01 ft.

## Groundwater

`/groundwater` covers TWDB's recorder-well network — around 400 wells across 24
aquifers (Ogallala, Edwards-Trinity, Carrizo-Wilcox…). Groundwater supplies
roughly half the water used in Texas and is invisible in reservoir data.

Three things this data will punish you for getting wrong:

- **Levels are feet _below land surface_.** A larger number is a deeper water
  table, so an increase is a *decline* — the opposite of reservoir levels. The
  well chart's Y axis is reversed for this reason, and the UI never prints a
  bare signed number; it says "3.3 ft lower".
- **Wells sit at different land elevations**, so depths are not comparable
  between wells. Only a single well's change over time means anything.
- **"Recent conditions" is not recent.** The feed returns each well's latest
  value regardless of age: 271 wells reported within 7 days, but 125 are over a
  year stale and some date to 2008. Anything older than 30 days is excluded from
  current-conditions views and flagged on the well page.

Per-well history is served only as the complete hourly record — over 100,000
rows and ~5 MB, with no date filtering and newest-first ordering — so it is
reduced to daily readings and memoised rather than cached by Next.

## Loading states

Navigation is where the real waiting happens — lake and well pages render on
demand from several upstream APIs. Measured cold, uncached:

| Route | Cold | Warm (memoised) |
| --- | --- | --- |
| `/lake/canyon` | 462 ms | 54 ms |
| `/lake/whitney` | **11.2 s** | — |
| `/groundwater/0260303` | 1.8 s | 47 ms |

Three mechanisms cover it:

- **`loading.tsx` skeletons** for `/lake/[slug]`, `/groundwater/[well]`, and a
  generic root fallback. Verified streaming: on a cold lake page the first byte
  including the skeleton arrives at **98 ms** while full content lands at
  **6.1 s** — so the shell appears immediately instead of the browser sitting on
  the old page.
- **`useLinkStatus` spinners** on the links people actually click (table rows,
  mobile cards, rank lists, basin lists, map popups, header nav). Without one, a
  click on a slow lake looks like it did nothing.
- **`useTransition`** on the two genuinely heavy client updates — the map's
  drought overlay (re-renders 254 county paths) and the well chart's "Full
  record" span (thousands of SVG points).

Deliberately **not** spinnered: the metric and window toggles on lake and
drought charts. Those are synchronous state changes over data already in memory,
and an indicator there is flicker, not feedback.

All indicators are gated behind a **120 ms delay** (`useDelayedPending`). Most
navigations resolve from cache in a few milliseconds, and a spinner that appears
and vanishes within one frame reads as jank.

### Hydration

`relativeTime()` reads `Date.now()`, so a gage age rendered as "27m ago" on the
server hydrates as "28m ago" on the client. That text mismatch threw React error
#418 and forced a client re-render of the whole root — which in turn delayed
every client component on the page. Its call sites now carry
`suppressHydrationWarning`, and the helper documents that requirement.

> **Known issue:** the 11.2 s cold load on `/lake/whitney` is a genuine
> performance problem, not just a feedback one. Lake pages fetch the full
> period-of-record CSV (up to ~1.9 MB) to compute percentiles, and TWDB is slow
> to serve it. Precomputing day-of-year statistics as a build step, the way
> slugs and flow gages already are, would remove this from the request path.

## Link previews

Shared links unfurl with a generated card in Slack, iMessage, Discord, Twitter
and anything else reading Open Graph tags. Every route sets `og:title`,
`og:description`, `og:url`, a canonical link and `twitter:card`.

Four bespoke images are generated at request time via `next/og`, all
1200×630 PNGs rendered in 8–210 ms:

| Route | Card shows |
| --- | --- |
| `/` | Statewide storage %, fill bar, reservoir and gage counts |
| `/lake/[slug]` | Lake name, % full, status, elevation vs pool, storage |
| `/drought` | Severity bar across Texas, D1+/D2+, DSCI, storage |
| `/groundwater/[well]` | Aquifer, county, depth to water |

Routes without a bespoke card (`/map`, `/basins`, `/groundwater`, `/about`)
point at the site-wide image explicitly. `opengraph-image` files apply only to
their own segment — they are **not** inherited by sibling routes — so without
that fallback those unfurls have no image at all.

The card generators read only cached summary feeds, never the period-of-record
history (1.9 MB per lake) or a well's full record (~5 MB). An unfurl that takes
longer than loading the page is worse than no unfurl.

### Two things to know

- **`NEXT_PUBLIC_SITE_URL` must be set at build time**, not just at runtime.
  Statically prerendered routes bake `metadataBase` in during the build, so a
  runtime-only value leaves `/`, `/drought` and `/map` advertising the fallback
  origin while dynamic routes use the real one. On Vercel,
  `VERCEL_PROJECT_PRODUCTION_URL` is picked up automatically.
- **Satori renders these, not a browser.** Flexbox only, no grid, and any
  element with more than one child needs an explicit `display: flex` — adjacent
  text nodes count, so interpolated strings must be built as a single template
  literal rather than `{count} reservoirs`. Getting this wrong fails the build,
  not just the image.

## Responsive behaviour

Breakpoints: phones below `sm` (640px), tablets `sm`–`lg`, the full data table at
`lg` (1024px) and up — so iPad portrait (768px) gets the tablet treatment and
iPad landscape (1024px) gets the desktop table.

### Navigation

The header nav collapses to a dropdown when the links stop fitting. The trigger
is **measured, not a breakpoint**: an off-screen copy of the full row stays
mounted and a `ResizeObserver` compares its natural width against the space
actually available. That keeps it correct at any viewport — phone, iPad portrait
and landscape alike — and stays correct if nav items are added later, which a
hard-coded breakpoint would not.

Measured live: the six links need **478px**; the row collapses once the nav has
460px and expands again at 660px. The gap between those is deliberate — a
`HYSTERESIS_PX` buffer, without which the width that collapses the row is also
the width that fits it, and dragging a window across that point oscillates.

The collapsed button shows the **current page name**, so the header still says
where you are. The menu closes on Escape (returning focus to the button),
outside click, item click, and on navigation. It stores the route it was opened
on rather than a boolean, so "close on navigate" and "close when the row expands"
are derived rather than chased with effects.

- **The reservoir list has two renderings.** Below `lg` the seven-column table
  would force ~46rem of horizontal scrolling, so it becomes stacked cards
  carrying the same fields, with a sort `<select>` standing in for the clickable
  column headers. Both render from the same filtered rows and both ship in the
  HTML, toggled by CSS rather than JS — that keeps SSR correct and avoids layout
  shift. The duplication costs ~110 KB of raw HTML on `/` but only a few KB
  gzipped, since the two views compress against each other.
- **The map switches interaction model on touch.** A hover tooltip is
  unreachable without a pointer, so on `(hover: none)` devices a tap *selects* a
  reservoir and opens a card containing the link, rather than navigating on first
  touch — markers are dense enough that tap-to-navigate means constant mis-taps.
  Marker radius also gets a floor on touch, because the 900-unit viewBox squeezed
  into ~350 CSS px would otherwise render the smallest reservoirs at ~1.4px.
- **Inputs are 16px on touch devices**, which is the threshold below which iOS
  Safari zooms the page on focus.
- `useMediaQuery` (`src/lib/useMediaQuery.ts`) is reserved for behaviour CSS
  can't express. It uses `useSyncExternalStore`, and returns `false` during SSR
  and hydration — so callers must pick a default that is safe in that state.

## Development

```bash
npm install
npm run dev          # http://localhost:3000
npm run build        # origin comes from .env.production (see Link previews)
npm test             # vitest, offline

npm run sync:slugs        # TWDB reservoir key -> URL slug
npm run sync:counties     # Texas county basemap geometry
npm run sync:flow         # reservoir -> river gage mapping (slow; ~2 NLDI calls/lake)
npm run sync:usace        # USACE CWMS series for lakes with no USGS gage
npm run sync:history      # per-lake period-of-record series (slow; 122 downloads)
npm run sync:percentiles  # monthly streamflow percentile thresholds (~60 batches)
npm run generate:emblem   # not a sync — rebuilds icons from the master emblem PNG
```

The `sync:*` scripts write into `src/data/` and `public/history/`, and their
output is committed. Nothing regenerates at request time, so a stale checkout
serves stale normals rather than failing.

They also run on a schedule — `.github/workflows/data-refresh.yml`, quarterly,
also runnable by hand from the Actions tab with a choice of which scripts to
run. It opens a **pull request** rather than pushing: this data decides what
the maps and percentile bands claim is normal, and a silent commit that shifts
every reservoir's normal range is not something to find out about later. The
run verifies typecheck, tests and a full Workers build against the regenerated
data before proposing it, because a pull request opened with `GITHUB_TOKEN`
does not trigger CI. Quarterly is deliberate: period-of-record normals barely
move in three months, and a monthly run would mostly produce 10 MB diffs of
noise.

### Tests

`tests/` covers the upstream parsers, the pure calculations they feed, and the
sync scripts, with vitest. Every case is a fixture reproducing a real quirk of
a feed — USGS's `-999999` sentinel and the column-width row that RDB puts where
data should be, TWDB's comment preamble and name-addressed columns, NWPS
publishing forecast flow in kcfs, CoCoRaHS rows arriving unordered — because
the failure mode that matters for this site is a **silently wrong number**
rather than a crash. Nothing touches the network, so the suite runs in well
under a second and cannot fail because an agency is having a bad day.

The sync scripts are testable because each runs `main()` only when executed
directly:

```js
if (process.argv[1] && import.meta.url === pathToFileURL(process.argv[1]).href) {
```

Importing one therefore yields its parsers without starting a multi-minute
download. TypeScript still checks those imports through `allowJs`, so a test
calling `encode()` is told it can return null.

Two rules keep the suite useful. Assert the *quirk*, not the happy path: a test
that only proves well-formed input parses would not have caught anything real.
And when a parser changes, add the malformed input that motivated the change.

Writing these found two live bugs, both the same shape. `Number(null)` and
`Number("")` are each `0`, so a guard of the form
`Number.isFinite(Number(cell))` accepts an absent value and publishes a zero:
CoCoRaHS rows with no measurement counted as stations reporting no rain and
pulled the "average across N stations" figure down, and a blank USGS percentile
would have been written as a `0` threshold — which reads as "any trickle is
normal or better". The committed percentile data was checked afterwards and is
clean, so that one was caught before it ever bit.

## Deploying to Cloudflare Workers

**Live: https://lbjtaskforce.com** (and `www.`)

Runs on Workers via the [OpenNext Cloudflare adapter](https://opennext.js.org/cloudflare).
All pages, both API routes and all four `next/og` image routes are verified
working in production.

### Domains

Both hostnames are Custom Domains on the `lbjtaskforce.com` zone, declared under
`routes` in `wrangler.jsonc` with `custom_domain: true` — Cloudflare creates the
DNS records and issues certificates automatically. Allow ~30 s after the first
deploy to a new hostname for the certificate to be issued; requests fail until
it is.

`workers.dev` is **disabled**. Note that wrangler turns it off by default as
soon as `routes` is present unless `"workers_dev": true` is set explicitly, so
the old `texas-lake-levels.<account-subdomain>.workers.dev` URL now returns 404.

Canonical tags and `og:url` point at the apex, so `www` serving the same Worker
is not treated as duplicate content.

### HTTPS

Two separate pieces, both required:

- **Always Use HTTPS** is enabled on the zone (SSL/TLS → Edge Certificates).
  It is **off by default on new zones**, and without it plain HTTP serves the
  site with a `200` rather than redirecting — so typing the bare domain lands on
  `http://` and browsers label it "Not secure" even though the certificate is
  perfectly valid. It is a zone setting, not something wrangler can configure.
- **HSTS** (`max-age=31536000`) is sent by the app itself, via `headers()` in
  `next.config.ts`. After one HTTPS visit a browser refuses to try HTTP for the
  host again. Deliberately no `includeSubDomains` or `preload` — both are sticky
  in browser caches and would commit every future subdomain to HTTPS-only.

Certificates are issued automatically by Cloudflare (Google Trust Services,
covering apex and `www`), so there is no certificate management to do.

### One-time setup

```bash
npx wrangler login

# Create the ISR cache namespace, then put the returned id in wrangler.jsonc.
npx wrangler kv namespace create NEXT_INC_CACHE_KV
```

A `workers.dev` subdomain must also be registered on the account before the
first deploy (Workers → onboarding in the dashboard). KV namespace ids are
account-scoped, so switching accounts means recreating the namespace.

### Deploy

Pushing to `main` deploys automatically — see **Continuous deployment** below.
To deploy by hand, or to recover when Workers Builds is unavailable:

```bash
npm run cf:deploy
```

The origin is no longer passed on the command line: `NEXT_PUBLIC_SITE_URL` lives
in the committed `.env.production` (build time, for prerendered canonical and
`og:image` URLs) and in `vars` in `wrangler.jsonc` (runtime, for dynamic routes
and ISR re-renders). Both are needed — with neither, links unfurl with a
`localhost` image URL. If a previous build baked in the wrong value, clear
`.next` and `.open-next` first: Next reuses prerendered output, so a stale
origin survives a plain rebuild.

`npm run cf:preview` builds and serves the real Worker locally first — use it
before deploying, since `next dev` runs in Node and will not catch runtime
incompatibilities. `npm run cf:typegen` regenerates binding types.

On Windows, a `workerd` process left behind by a previous `cf:preview` keeps a
handle on `.open-next/`, and the next build dies with `EPERM ... rm`. Stop the
process, delete the directory, and rerun.

### Continuous deployment

**Cloudflare Workers Builds** deploys this repository. It watches `main` and
builds inside Cloudflare's own infrastructure, which is the reason to prefer it
over deploying from GitHub Actions: **no Cloudflare credential is stored
outside Cloudflare.** Configure it under Workers &amp; Pages → the Worker →
Settings → Build, connecting the GitHub repository through Cloudflare's GitHub
App:

| Setting | Value |
| --- | --- |
| Build command | `npm run cf:build` |
| Deploy command | `npx opennextjs-cloudflare deploy` |
| Branch | `main` |
| Root directory | `/` |

Non-production branches can be enabled for preview builds; they publish
[preview URLs](https://developers.cloudflare.com/workers/configuration/previews/)
rather than touching production.

No build variables are needed — `NEXT_PUBLIC_SITE_URL` is committed in
`.env.production`, which is exactly why it lives there rather than being passed
on the command line.

An API-token deployment from GitHub Actions was tried first and abandoned. It
works, but the token has to carry **Zone → Workers Routes → Edit** on top of
the Workers and KV permissions, because `wrangler deploy` reconciles the
`custom_domain` routes in `wrangler.jsonc` against the zone — and that is a
broad credential to keep in a third-party system for a site that Cloudflare can
just build itself.

`.github/workflows/ci.yml` remains, and now only typechecks, lints and builds.
It never publishes, so it needs no secrets at all: it catches type errors, lint
failures and broken builds on a pull request, before Workers Builds sees the
commit.

Note that the build prerenders pages, which fetches TWDB, USGS, NWPS, USDM and
CoCoRaHS — an upstream outage can fail a build that has nothing wrong with it,
and the dashboard in particular fetches TWDB without a fallback. Retry the
build; if Workers Builds is down, `npm run cf:deploy` from a workstation still
works, since wrangler's own OAuth login is unaffected by any of this.

### The KV cache is not optional

Every ISR route here is ultimately backed by TWDB, USGS or USDM, and TWDB
throttles bursts with 502/503. Without a shared incremental cache each isolate
regenerates independently and hammers upstream. KV gives all isolates one cache;
`withRegionalCache` keeps repeat reads inside a colo from returning to KV each
time.

### Two-layer caching for expensive derivations

Lake and well pages derive their statistics from very large CSVs — up to 1.9 MB
and ~30,600 rows for a reservoir's period of record, ~5 MB and 100,000 rows for
a well. Those derivations sit behind `unstable_cache`, which persists the small
derived result (tens of KB) through the incremental cache — Workers KV in
production.

The in-process `Map` in each module is only an L1. That distinction is the whole
point on Workers: isolates are short-lived and each gets its own memory, so an
in-process memo alone is missed by nearly every request. Measured on the
deployed Worker before and after adding the persistent layer:

| Route | Before | After (cold) | After (warm) |
| --- | --- | --- | --- |
| `/lake/travis` | 39.5 s | 3.3 s | 0.32 s |
| `/lake/canyon` | 27.8 s | 1.1 s | 0.74 s |
| `/groundwater/0260303` | 1.4 s | 1.6 s | 0.11 s |

Precomputed history (above) then removed most of the remaining cold cost.
Measured across a fresh sample of eight lake pages after a deploy, with an empty
cache: **median 941 ms, min 852 ms, max 8.8 s** — against 28–43 s at the worst
before either change. Warm pages run 195–970 ms.

The remaining spread is upstream latency, not parsing: a cold lake page still
fans out to TWDB, USGS, USDM and sometimes USACE, and any one of them being slow
sets the total.

## Routes

| Route | Description |
| --- | --- |
| `/` | Statewide dashboard: summary stats, low/full rankings, sortable table |
| `/map` | Reservoirs by fill status, plus toggleable river-gage and drought layers |

`/sitemap.xml` enumerates every route including all lake and well pages — the

keeping them out of `/api/`. Both are generated from the same cached feeds the
pages use.

### JSON API

```
GET /api/lakes            ?basin=Colorado   ?status=critical
GET /api/lakes/:slug      ?range=30day|1year|all   ?gage=1   ?context=1   ?flow=1
```

`?context=1` adds period-of-record percentiles; `?flow=1` adds inflow/release
river gages.

`?format=csv` on either endpoint returns a spreadsheet-friendly download
instead of JSON — the statewide snapshot as one row per reservoir, or a lake's
daily history for the requested `range`. The lake pages and dashboard link to
these as "Download CSV".

Both return `502` with a detail message if upstream is unavailable, and
`/api/lakes/:slug` returns `404` for an unknown reservoir.

## Notes on the numbers

- **Percent full** is conservation storage ÷ conservation capacity. It exceeds
  100% when a lake rises into its flood pool — normal and temporary.
- **Statewide and basin figures are storage-weighted**, not averages of
  percentages, so Toledo Bend counts for far more than a small municipal lake.
- USGS and TWDB elevations for the same lake can differ slightly due to vertical
  datum (NAVD88 vs NGVD29) and reading time.

## Ideas for expansion

Verified available, not yet built:

- **Water temperature** — 103 active TX sites (param 00010), opens a
  recreation/fishing audience.
- **County drought history behind each lake's chart** — the USDM county endpoint
  accepts date ranges back to 2000, so per-lake drought context is one request
  away.
- **Groundwater trends** — per-well change over time is computed on the well
  page, but a statewide "which aquifers are declining fastest" view would need
  the 5 MB per-well CSVs precomputed as a build step.
- **IBWC** (Amistad, Falcon) and **Bureau of Reclamation** (Elephant Butte) —
  the remaining reservoirs with no real-time source here.
- **NWS forecasts** (`api.weather.gov`) — watershed precipitation ahead of a lake.
- **Alerting** on level or rate-of-change thresholds. Serves every audience but
  is the only item needing real infrastructure: database, cron, email delivery.
